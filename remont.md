**Дата:** 2026-08-30
**Коммиты:** `26ad6f2` (#0001 Fix all), `6507c8d` (#0001 Fix server - SPA fallback)

Документ отвечает на два вопроса: **что именно** было решено сделать в каждой правке и **почему** выбран именно этот путь — с альтернативами, которые рассматривались и были отвергнуты, и с осознанными компромиссами.

## 1. Контекст и методология

### 1.1 Исходное состояние

Репозиторий — учебно-демонстрационное приложение на React 19 + react-router 7 + effector + express 5 с **самописной i18n-механикой**: ленивый фетч переводов по ключам с дебаунсом, сервер отдаёт плоские yaml-словари. В зависимостях нет i18next/react-intl — и это осмысленно: **смысл репозитория в собственном механизме**, а не в обёртке над библиотекой.

Первичный аудит выявил: 4 ошибки и 2 предупреждения ESLint, 3 критичных бага (битая навигация со вложенных страниц, гонка ответов, неработающая смена языка), пачку средних и мелких проблем.

### 1.2 Принципы, по которым принимались решения

1. **Чинить механизм, а не заменять.** Рассматривался путь «возьми i18next и не мучайся» — отвергнут: репозиторий существует ради демонстрации собственной механики, замена обесценила бы код.
2. **Минимальный дифф при сохранении публичных контрактов.** Каждый ломающий момент (единственный — формат `%s`) проходил проверку вопросом «можно ли починить, не меняя API?». Если да — менял, если нет — менял формат и обновлял **все** точки использования за один заход.
3. **Эмпирика перед теорией.** Прежде чем чинить react-router и express-поведение, я **воспроизвёл** его тестами (`matchRoutes`, `resolvePath`, `renderToString`, живые curl-запросы). Ревью «по-моему так» не аргумент.
4. **Промежуточная верификация после каждого блока**, а не одна в конце — это дважды поймало мои собственные ошибки до того, как они уехали в следующие правки.
5. **Живой запуск обязателен.** Статический анализ не нашёл бы отсутствующий SPA-fallback — его нашёл только запуск приложения и открытие страниц.

## 2. Ядро i18n

### 2.1 Гонка ответов в TranslateProvider

**Проблема.** `updateTranslate` делал `setTranslate({ ...translate, ...result })`, где `translate` — снапшот из замыкания рендера. Два запроса в полёте → ответ более позднего запроса затирается устаревшим снапшотом. Часть переводов навсегда откатывается на сырые ключи до следующего полного сброса.

**Рассмотренные пути:**
- **(а) Функциональный апдейт** `setTranslate(prev => ({ ...prev, ...result }))`;
- (б) AbortController — отменять устаревшие запросы;
- (в) Счётчик/маркер запроса — игнорировать ответы не из последней волны;
- (г) Очередь с сериализацией запросов.

**Решение: (а).**

**Почему.** Варианты (б)–(в) лечат более широкую задачу — рассинхронизацию по языку, — но требуют состояния/жизненного цикла вне React и заметно усложняют код провайдера. А **конкретный** баг из аудита (потеря результатов из-за устаревшего снапшота) закрывается однострочно и идиоматично: слияние через `prev` делает финальное состояние надмножеством обоих ответов, и «затирание» исчезает по определению. Параметр `translate` у `updateTranslate` стал не нужен — сигнатура упростилась.

**Компромисс (честно):** остаточная гонка при **смене языка** осталась теоретически возможной: ответ старого языка, пришедший после очистки `translate`, домержит русские строки в английское состояние. Окно мало (миллисекунды), но не нулевое. Полное лечение — страж «lang запроса ≠ lang текущий → игнор» в `updateTranslate` либо AbortController по языку. Не сделано в этом заходе, потому что требует протаскивания `lang` в слияние и отдельного теста; зафиксировано как известное ограничение (см. §7).

### 2.2 Перезагрузка переводов при смене языка

**Проблема.** Эффект загрузки зависел только от внешнего пропа `deps` (`[location.pathname, globalNum]` из `App`). `useSetLang` очищал `translate`, но фетч не триггерился — работало лишь побочно, потому что LangSwitcher заодно навигировал на главную и менял pathname. Хук как публичный API был сломан.

**Рассмотренные пути:**
- **(а) Добавить `lang`/`translate`/`debouncedFetch` в зависимости эффекта** внутри провайдера;
- (б) Отдельный эффект на `[lang]`;
- (в) Убрать проп `deps` совсем и завязаться только на внутреннее состояние.

**Решение: (а).**

**Почему.** Очистка `translate` (`setTranslate({})`) меняет ссылку стейта → эффект с зависимостью `translate` гарантированно переходит, видит пустой стейт, вычисляет diff по `translateKeys` и делает фетч. Один эффект обслуживает **все** причины перезагрузки (смена языка, навигация, новые ключи) — вместо дублирования логики в (б). Вариант (в) красивее архитектурно, но ломает публичный API провайдера, который использует `App` (задача аудита — чинить, а не перепроектировать), поэтому `deps` оставлен как дополнительный триггер.

**Компромисс:** проп-массив зависимостей — известный анти-паттерн React. Он остался сознательно: API провайдера — публичный контракт этого учебного репозитория. ESLint при этом чист (массив стал литералом, включающим `deps`).

### 2.3 sprintf: `%` → `%s` (единственное ломающее изменение)

**Проблема.** `sprintf` рекурсивно делал `str.replace("%", argv.shift())` по **уже заменённой** строке. Значение-подстановка, содержащее `%`, перехватывало следующую замену: `__('%', '100%')` → `'1002'`. Хуже того: при формате с голым `%` **ни одна строка переводов не может содержать литеральный процент** — он всегда станет плейсхолдером.

**Рассмотренные пути:**
- (а) Лечить старый формат: заменять `%` только по позициям исходной строки, не трогая подстановки;
- **(б) Явный плейсхолдер `%s`** с заменой по регулярке;
- (в) Именованные плейсхолдеры `{0}` / `{name}`;
- (г) Экранирование `%%`.

**Решение: (б).**

**Почему.** (а) сохраняет совместимость, но навсегда оставляет запрет на литеральный `%` в переводах — дефект формата, а не реализации. (в) — лучший формат для больших проектов, но для позиционного API gettext-стиля избыточен и потребовал бы переписывать все вызовы всё равно. (г) — полумера: экранирование надо помнить и в yaml, и в коде. `%s` даёт: явный маркер (литеральный `%` свободен), знакомый по C/PHP синтаксис, минимальную реализацию (`replace(/%s/g, cb)`) и предсказуемое поведение при нехватке аргументов (плейсхолдер остаётся видимым — ошибка заметна глазами).

**Цена.** Обновлены ключи `Page%`→`Page%s`, `Condition %`→`Condition %s` в трёх yaml и **19 вызовов** `__()`/`t()` в 7 компонентах — за один коммит, чтобы формат никогда не существовал в двух вариантах.

### 2.4 Вынос контекста в `context.ts`

**Проблема.** ESLint: `react-refresh/only-export-components` — файл экспортирует и компонент, и контекст; fast refresh для такого файла деградирует (при правке провайдера перерисовывается всё дерево с потерей состояния).

**Решение:** `createContext` вынесен в `src/i18n/context.ts`, провайдер и хуки импортируют оттуда.

**Почему.** Это не формальность ради линтера: побочный эффект — хуки больше не импортируют из модуля компонента, что убирает потенциальный цикл импортов и делает `hooks.ts` самодостаточным. Альтернатива «отключить правило» отвергнута: правило чинит реальную механику HMR, а не вкус.

### 2.5 Мутация состояния в updateTranslate (LRU-ветка)

**Проблема.** `keys.forEach(key => delete translate[key])` — `delete` по объекту из `useState`. Работало «случайно» (дальше шёл спред), но мутирование стейта ломает контракты React (мемоизация, time-travel) и маскирует баги.

**Решение:** вся эвикция переписана **внутри** функционального апдейтера: копия `{ ...translate }`, удаление на копии, возврат нового объекта. Ветер включается только при `limit !== null`.

**Почему не удалил ветку совсем** (она мертва — `limit = null`): это задокументированная возможность конфига («cache limit in pairs»), автор явно оставил её намеренно. Починил, а не выкорчевал. Мёртвым удалял только то, что не имеет ни потребителей, ни документированного смысла (§6.1).

### 2.6 useDebounce: типизация и unmount

**Проблема-1:** `<T extends (...args: any[]) => void>` — две ESLint-ошибки `no-explicit-any` в проекте жили здесь и в `sprintf`.
**Решение-1:** generic сменён на `<A extends unknown[]>` — типы аргументов колбэка выводятся, `any` не нужен.

**Проблема-2:** таймер не чистился при размонтировании — колбэк мог выстрелить после unmount (setState на размонтированном компоненте, утечка).
**Решение-2:** `useEffect(() => () => clearTimeout(...), [])`.

**Почему.** Обе правки — гигиена без изменения поведения: дебаунс остаётся прозрачной обёрткой. Альтернатива «переписать на ref-based debounce-объект» отвергнута как усложнение без выигрыша для одного потребителя.

### 2.7 .catch на фетч

**Решение:** `.catch(console.error)` в провайдере.

**Почему именно так, а не error-state + UI:** перевод — некритичный декоративный слой; при падении API приложение обязано продолжать работать на сырых ключах (это и есть его фолбэк-поведение), ошибка должна быть **видна в консоли**, но не обязана иметь UX. Полноценная обработка ошибок — отдельная фича, не ремонт.

## 3. Навигация

### 3.1 Ведущий слэш в LangLink (критичный баг №1)

**Проблема.** `LangLink` собирал `'ru/page/1'` **без** ведущего `/`. React-router v7 резолвит такие ссылки относительно **текущего** URL: со страницы `/ru/page/2` ссылка «Page 1» давала `href="/ru/page/2/ru/page/1"` → роут `:lang?/*` → 404. Проверено рендер-тестом до фикса: все три ссылки со вложенной страницы были битыми.

**Рассмотренные пути:**
- **(а) Строить абсолютный путь:** `'/' + [prefix, link].filter(Boolean).join('/')`;
- (б) Вернуть `to` как был и полагаться на относительную резолюцию react-router;
- (в) Считать префикс через `params` роута.

**Решение: (а).**

**Почему.** Контракт `LangLink` — «путь от корня с языковым префиксом»; это же ожидание заложено в единственном месте его использования (`MenuItem` передаёт `/page/N`). (б) требует переосмысления контракта и всё равно ломается на вложенности — относительная резолюция и не была задумана. (в) — лишняя связка компонента с конкретной схемой роутов. `filter(Boolean)` заодно убирает пустой сегмент при `prefix=''` (язык по умолчанию), что в старом коде давало `'/' + '' + '/' + 'page/1'` → `'//page/1'` после join... точнее — мусорный пустой сегмент.

**Верификация:** рендер-тест с `MemoryRouter` подтвердил `/ru`, `/ru/page/1`, `/page/1` со страницы `/ru/page/2`.

### 3.2 Валидный HTML: `<ul><a><li>` → `<ul><li><a>`

**Проблема.** `<Link><li/></Link>` внутри `<ul>`: прямым ребёнком `<ul>` может быть только `<li>` (плюс script/template). Невалидная разметка — риск в гидратации и для a11y-инструментов.

**Решение:** перевёрнуто в `<li className=...><Link>…</Link></li>` в `LangItem` и `MenuItem`.

**Почему классы и onClick остались на `li`:** daisyUI `menu` оперирует классами на `li` (`menu-active`, `hover:menu-active`) — скриншоты живого приложения подтвердили, что подсветка активного пункта работает. Перенос обработчика на `Link` изменил бы область клика (только текст ссылки vs весь пункт) — сохранил исходное поведение.

### 3.3 Валидация `:lang` — мягкий 404

**Проблема.** Роут `:lang?/` матчит **любой** первый сегмент: `/rux` рендерил HomePage с «языком» `rux`, пустыми переводами и URL, который потом кэшируется в детекции языка.

**Рассмотренные пути:**
- **(а) Guard в компонентах** (`HomePage`, `PageWrapper`): параметр задан, но не в `SUPPORTED_LANGS` → 404;
- (б) Кастомный матчер роутов / data-router loader с валидацией;
- (в) Регулярка в path роута (`:lang(ru|de)`-стиль).

**Решение: (а).**

**Почему.** Приложение использует декларативный `BrowserRouter` + `Routes` без data-возможностей — (б) потребовал бы миграции на `createBrowserRouter`, непропорциональной задаче. (в) в react-router 7 не поддерживает regex-ограничения сегментов в декларативном режиме. Guard в двух точках входа — минимальное изменение с дублированием в три строки, которое честно задокументировано как компромисс.

## 4. Сервер

### 4.1 Пути от `import.meta.url`

**Проблема.** `path.resolve('./', 'src/server/data', ...)` — разрешение от **cwd процесса**. `npm run serve` из корня работало, запуск из любого другого каталога молча возвращал `{}` (ветка `existsSync === false`) — диагностировать такое труднее, чем упасть.

**Решение:** `dataDir` от `fileURLToPath(import.meta.url)` — так же, как уже был написан `staticRootUrl` в `server.js`.

**Почему.** В одном файле проекта уже существовал правильный паттерн — задача свелась к консистентности, а не к изобретению. Альтернатива `process.cwd()` + документация «запускать только из корня» — это фиксация дефекта, а не ремонт.

### 4.2 Кэш yaml по mtime

**Проблема.** `readFileSync` + `parse` на **каждый** запрос — и чтение диска, и парсинг при неизменном файле.

**Рассмотренные пути:**
- (а) Кэш навсегда (Map без инвалидации);
- **(б) Кэш + проверка `mtime`** (`statSync` на запрос);
- (в) `fs.watch`/chokidar для инвалидации по событию.

**Решение: (б).**

**Почему.** (а) ломает dev-цикл «правишь yaml без перезапуска» — главный сценарий учебного репозитория. (в) — сложность (жизненный цикл watcher'а, платформенные особенности) непропорциональна трём файлам словарей. (б) даёт O(1) на запрос без парсинга: один `statSync` — дешёвый syscall против чтения+`yaml.parse`. Компромисс: при внешнем изменении с точностью до mtime-кванта возможен редкий устаревший ответ — приемлемо для словарей на 25 строк.

### 4.3 Валидация запроса

**Проблемы.** (1) Не-JSON тело → `req.body` undefined → `TypeError` на `req.body.filter` → 500. (2) `filter` не-массив → `keys.map` кинет. (3) `acceptsLanguages` при отсутствии совпадений возвращает `false` → сервер искал файл `false.yaml` → молча `{}`.

**Решение:** `req.body?.filter`; `Array.isArray` + отсечение не-строк; `detectLang` с фолбэком на `'en'`.

**Почему фолбэк, а не 400.** Рассматривал строгий вариант — отвечать 400 на мусор. Отверг: API переводов — вспомогательный, его контракт с клиентом («дай что есть, недостающее клиент дорисует ключами») естественно деградирует. Отсечение не-строк молча (а не ошибкой) — по той же причине: строка-мусор в фильтре не должна ронять ответ целиком.

### 4.4 SPA-fallback — баг, найденный живым запуском

**Проблема.** Выявлена только при запуске приложения: hard refresh `/ru/page/2` отдавал **404 от сервера** — express раздавал статику, но не имел fallback на `index.html` для клиентских маршрутов. Статическое ревью это пропустило: код «не содержал ошибки», в нём **отсутствовала функция**.

**Рассмотренные пути:**
- **(а) Regex-роут `app.get(/^\/(?!api\/).*/, sendFile(index.html))` перед 404-обработчиком;**
- (б) Пакет `connect-history-api-fallback`;
- (в) Catch-all `app.use(...)` на все методы.

**Решение: (а).**

**Почему.** В express 5 (path-to-regexp v8) строковый wildcard `'*'` больше не работает как в v4 — потребовались бы именованные wildcard'ы; regex явнее и не зависит от конвенций версии. (б) — внешняя зависимость ради шести строк. (в) ловил бы и POST на неизвестные пути (должны быть 404) и требовал бы дополнительных условий внутри. Regex с negative lookahead `(?!api/)` оставляет `/api/*` честный 404 и вешается только на GET — ровно семантика SPA.

**Компромисс:** неизвестный путь вроде `/nope.js` теперь отдаёт 200 с HTML вместо 404. Это стандартное поведение SPA-fallback; клиентский роутер отрисует свой 404 (`:lang?/*` → `ErrorCmp`). Для API-путей поведение не изменилось.

## 5. Переводы

**Решение 1: en.yaml как источник паритета.** В `en` (язык по умолчанию!) отсутствовали 11 ключей, имеющихся в ru/de — дефолтный язык показывал сырые ключи, хотя по смыслу именно он должен быть полным. Ключи доведены до паритета en=ru=de и **проверены diff'ом** — это дешёвая механическая проверка, которую легко повторить.

**Решение 2: не менять структуру словарей.** Плоские ключи (`Object.hasOwn` на верхнем уровне) — контракт сервера; вложенные namespace'ы были бы лучше для большого проекта, но потребовали бы переписывания и клиента, и сервера. Ремонт не перепроектирование.

**Решение 3: смысловые опечатки правились наравне с орфографическими.** «голобальном»→«глобальном» (ru, ×2) — орфография; `Cond2Key: Inhalte unterliegen 3`→`... 2` (de) — **фактическая** ошибка: текст «условия 2» говорил «3». Второй класс опаснее первого и легко бы остался при «проверке орфографии».

## 6. Чистка

### 6.1 Критерий удаления мёртвого кода

Удалял по правилу: **нет потребителей И нет документированного смысла** — удалить; есть задокументированный смысл — починить/оставить (пример — LRU-ветка, §2.5). По этому критерию ушли: тип `Typet` (пустой алиас), `FetchTranslateType` (нигде не реализуется), `fetchAllMap` + `detectLangByAttribute` (альтернативные пути, отключённые закомментированными импортами в config), дубликат иконки `icons/Lang.tsx` (байт-в-байт копия `LangSwitcher/Icon.tsx`), мёртвое `result = {}` в конце `updateTranslate`. Закомментированные импорты в `config.ts` удалял вместе с их целями: git-история хранит выключенный код лучше, чем файл с 8 строками комментариев.

Переименование `Sanwich.tsx` → `Sandwich.tsx` сделано **через `git mv`** — сохраняет rename-detection в истории (blame/log следуют за файлом), что важно именно в учебном репозитории, где история — часть материала.

### 6.2 Modal: флаг вместо JSX в effector-сторе

**Проблема.** `modalOpened(<ModalContents />)` клал React-элемент в стор. Элемент — это замороженный снимок рендера **в момент создания**: он несёт пропы и контекст того места, откуда создан; в effector-сторе он переживёт своё окружение, ломает сериализацию/devtools и смешивает слои (store знает о view).

**Решение:** стор хранит булев флаг `$modalOpened`; `Modal` сам импортирует и рендерит `ModalContents`.

**Компромисс честно:** модалка потеряла универсальность («открыть произвольный контент») и стала знать о конкретном содержимом. Для репозитория с **одной** модалкой это правильный YAGNI-обмен: когда появится вторая, флаг превратится в union-тип `'contents' | 'other' | null` — назад к универсальности вернуться дёшево, а хранить JSX в сторе дорого сразу.

### 6.3 Поведенческие мелочи, ставшие исправлениями

- **Закрытие модалки по Esc и клику на подложку** — базовое ожидание UX; листнер Esc ставится только при открытой модалке (без постоянного глобального слушателя). Нативный `<dialog>.showModal()` с фокус-трапом рассматривался — требует ref-менеджмента и меняет стилизацию; зафиксировано как возможное улучшение.
- **Двойной карринг** `const onClick = () => () => {...}` + `onClick={onClick()}` заменён обычной функцией: карринг здесь не давал ни переиспользования, ни частичного применения — только второй вызов на каждый рендер.
- **`(_, num) => num` в effector-хендлерах:** первый параметр `.on` — предыдущее состояние (корректно `_`), второй — payload события, который был назван `store`. Имена параметров — документация.

## 10. Итог

Ремонт выбран **хирургический**: починить каждый дефект до корня (гонка — до функционального апдейта, ссылки — до резолюции react-router, сервер — до контрактов данных), не заменяя ни механизм i18n, ни архитектуру провайдера, ни структуру словарей. Единственное ломающее изменение формата (`%s`) оправдано тем, что старый формат делал **невозможным** легитимный контент (литеральный `%` в переводах) — то есть был дефектом дизайна, а не реализации. Всё, что не починено, — перечислено в §7 с указанием пути лечения.
