# BIZ_REQs.md — требования и концепция: i18n как сервис

**Ветка:** `upgrade_i18n_service`
**Дата:** 2026-08-30
**Статус:** дизайн утверждён в диалоге, реализация не начата

---

## 1. Бизнес-требования

### BR-1. Использование переводов вне React

Переводы должны быть доступны из не-React кода: effector-эффекты, утилиты, любой модуль с прямым `import`. Сейчас `gettext` живёт только внутри `TranslateContext` — вне дерева компонент его получить нельзя.

### BR-2. Точечные ререндеры

Смена языка и подгрузка переводов перерисовывают только компоненты, читающие переводы. Сейчас `TranslateContext.Provider` пересоздаёт `value` на каждый мерж словаря — ререндерится всё дерево под провайдером.

### BR-3. Устранение известных компромиссов (remont.md §7)

- **§7.2 проп `deps`** — анти-паттерн «проп-массив зависимостей»; убирается как класс: провайдер исчезает, `App.tsx` перестаёт оборачивать дерево и передавать `[location.pathname, globalNum]`.
- **§7.1 остаточная гонка при смене языка** — ответ старого языка, пришедший после смены, не может загрязнить новый язык (см. §3.3 концепции: словари per-lang).
- **§7.6 ошибки только в консоль** — остаётся (переводы — декоративный слой, падение API не должно ломать UI); пересмотр не входит в объём.

### BR-4. Учебная цель: сервисный паттерн

Ядро i18n — фреймворк-агностичный plain-TS синглтон; React-часть — тонкие адаптеры (хуки). Ядро тестируется без React и без DOM. Репозиторий демонстрирует архитектуру, а не обёртку над библиотекой (remont.md §1.2.1 — механизм не заменяем).

## 2. Публичный контракт — что не меняется

Хуки `useTranslate`, `useSetLang`, `useLangPrefix` и сигнатура `t(key, ...argv)` остаются публичным API компонентов. Потребители (Navbar, Page1–3, ModalContents, LangSwitcher, LangLink) **не узнают о переезде**. Конфиг-константы (`SUPPORTED_LANGS`, `DEFAULT_LANG`, `delay`, `limit`, `defaultTranslateKeys`) сохраняются. Формат `%s` и плоские yaml-словари — без изменений.

## 3. Концепция (подход A): автономный сервис + тонкие адаптеры

### 3.1 Конвейер ленивого фетча — единственный механизм на оба сценария

Сбор ключей, дебаунс, фетч — забота сервиса, не React. Один конвейер обслуживает **и новые ключи, и смену языка**:

```
t(key) → ключа нет в словаре текущего языка → pending.add(key) → таймер (delay=50ms)
      → flush: батч pending → fetch(lang, keys) → merge в словарь этого языка → notify
```

Принятые решения (аргументированы в диалоге):

1. **Demand-driven сбор** — регистрация ключа происходит в самом `t()`: хук вызвал — ключ в очереди. Навигация отрисовывает новые компоненты, те зовут `t()`, конвейер подхватывает. Проп `deps` не нужен.
2. **Дебаунс — планировщик сервиса**, с in-flight дедупликацией: несколько `t()` за один тик → один запрос; ключ с летящим запросом повторно не ставится в очередь.
3. **Словари per-lang** (`Map<lang, Map<key, value>>`) — ответ мержится в словарь того языка, для которого фетчился. Гонка §7.1 умирает по построению: устаревший ответ ложится в кэш старого языка без notify. Бонус: возврат на загруженный язык — из кэша, без сети.
4. **Смена языка = тот же конвейер**: `setLang(lang)` → notify → ререндер → `t()` видит пустой словарь нового языка → регистрирует ключи → debounce → фетч. Прогрессивный рендер (сначала фолбэк, потом переводы) — сознательно: переводы декоративны, блокировать UI нечем (remont.md §2.7). Suspense/`ready`-флаги отвергнуты.
5. **Транспорт — инъекция**: ядро принимает `transport(lang, keys) => Promise<result>`; дефолт — текущий `fetchTranslate`. Тестируется на фейковом транспорте и фейковых таймерах.
6. **Точечные ререндеры — `useSyncExternalStore`**: подписка на сервис; ререндер только читателей.

### 3.2 Состав

- `src/i18n/service.ts` — ядро: класс с `t`, `setLang`, `getLang`, `subscribe`; конвейер из §3.1.
- `src/i18n/adapters.ts` (или расширение `hooks.ts`) — хуки на `useSyncExternalStore`, сигнатуры прежние.
- `TranslateProvider.tsx` — удаляется; `App.tsx` упрощается.
- Effector-зеркало (`$lang`, `$translate` через `subscribe`) — **вне объёма**, подключается отдельной задачей при первом не-React потребителе (YAGNI).

### 3.3 Отвергнутые альтернативы

- **B. Сервис на effector-юнитах** — ядро сращено с effector (против BR-4), батчинг+debounce+in-flight многословнее, синглтон-поведение effector даёт неохотно.
- **C. Гибрид «контекст + синглтон»** — два источника истины; отвергнут сразу.
- **Suspense/блокирующий рендер** — против прогрессивной философии проекта.

## 4. Компромиссы и известные ограничения

1. Мини-emitter в ядре (~15 строк) рядом с уже установленным effector — цена фреймворк-агностичности; принимается.
2. Прогрессивный рендер при смене языка: кадр с сырыми ключами до прихода фетча — сознательная политика, не дефект.
3. Кэш словарей per-lang не ограничен по памяти (`limit` из конфига продолжает действовать только как LRU-эвикция внутри текущего языка — если останется согласуемым; иначе помечается deprecated отдельным решением в плане).
4. Сервер (`/api/gettranslate`) не меняется.

## 5. Критерии верификации

- `eslint .` — 0/0; `tsc -b` — 0 ошибок; `vite build` — ✓.
- Юнит-тесты ядра (node, фейковый транспорт/таймеры): батчинг «N вызовов за тик → 1 запрос»; устаревший ответ не notify; смена языка и возврат — из кэша без сети; `%s`-подстановки.
- Живой запуск: смена языка, навигация по страницам, modal, hard refresh — поведение прежнее; Network: повторное включение языка не фетчит.
- Ререндеры: подтверждение, что при мерже словаря ререндерятся только читатели `useTranslate` (React Profiler или лог-пробы).
